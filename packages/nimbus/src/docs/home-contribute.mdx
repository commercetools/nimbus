# Contributing to nimbus

Product teams can propose pull requests directly to the nimbus repository.
Please read the [collaboration guidelines](/contribute/collaboration)
before contributing.

Before opening a PR:

1. **Discuss the change first.** Start in Slack or a GitHub Issue. The nimbus
   team can help scope the work, flag potential conflicts with in-progress work,
   and confirm the approach aligns with system conventions.
2. **Align on whether the change belongs in nimbus.** Not every useful component
   is a good fit for the core system. The nimbus team is the final
   decision-maker on what goes into nimbus, and an early conversation avoids
   wasted effort.
3. **Follow nimbus conventions.** Contributions should meet the same standards
   as nimbus-authored code: accessibility, testing, documentation, Figma parity,
   and API consistency. The nimbus team can help contributors understand these
   expectations.

The nimbus team reviews and shepherds contributed PRs. Some contributions may be
accepted as-is; others may be adapted or reimplemented to fit system
conventions. In all cases, the contributing team gets credit and the outcome is
collaborative.

## Guidelines in the repository

The guides for maintainers and contributors live in the `docs/` folder of the
[nimbus repository](https://github.com/commercetools/nimbus/tree/main/docs).
Read them before you write code.

| Guide                                                                                                                  | What it covers                                           |
| :--------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------- |
| [Component guidelines](https://github.com/commercetools/nimbus/blob/main/docs/component-guidelines.md)                 | How a component is built, from types to documentation    |
| [File type guidelines](https://github.com/commercetools/nimbus/tree/main/docs/file-type-guidelines)                    | Rules for each file type, such as recipes, stories, docs |
| [Naming conventions](https://github.com/commercetools/nimbus/blob/main/docs/naming-conventions.md)                     | Names of files, components, props and messages           |
| [Git conventions](https://github.com/commercetools/nimbus/blob/main/docs/git-conventions.md)                           | Branch names and commit messages                         |
| [Changeset conventions](https://github.com/commercetools/nimbus/blob/main/docs/changeset-conventions.md)               | What to write in a release note                          |

For the reasons behind the main decisions, read the [architecture decision records](/contribute/adrs).

## Communication channels

| Channel                                                                          | When to use                                                                                                 |
| :------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------- |
| [**nimbus Slack channel**](https://commercetools.slack.com/archives/C0ACFBKAHTM) | Quick questions, exploring whether something exists, early-stage feature discussions, architecture guidance |
| [**GitHub Issues**](https://github.com/commercetools/nimbus/issues)              | Formal bug reports, feature proposals (using the template), design discrepancy reports                      |
| [**Jira**](https://jira.commercetools.com)                                      | Tracking work in progress once a decision has been made                                                     |
