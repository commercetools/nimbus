Nimbus uses one color system for every component. Each color is a **palette**:
12 steps of one hue, plus a `contrast` step. Each step has one job, such as a
background, a border or a text color. And each step has a value for light mode
and a value for dark mode, so a design works in both modes without extra work.

Browse the palettes below, learn [how colors work](#how-colors-work), or go
straight to [using colors in code](#use-colors-in-code).

## How colors work

### Steps

A palette orders one hue by **contrast**, from subtle backgrounds to
high-contrast text. The steps fall into four groups:

- **Backgrounds (1–5):** from the app background to selected elements. Text on
  them uses steps 11 and 12.
- **Borders (6–8):** separators, element borders and focus rings.
- **Solid (9–10):** solid backgrounds and their hover state. Text on them uses
  the `contrast` step.
- **Text (11–12):** low-contrast and high-contrast text.

The colors in the table are from the `primary` palette.

### The contrast step

The `contrast` step is black or white, chosen for readability on steps 9 and 10
of its palette. Most palettes use white; a light palette such as `warning` uses
black. Use it for text on a solid background, for example the label of a solid
button.

### Three kinds of palettes

There are three kinds of palettes, plus the
[black and white palettes](#black-and-white-palettes). The palette browser shows
each kind in its own group:

- **Semantic palettes** have a meaning. They communicate a status or a state,
  for example an error or a success. Use them when a color has a meaning.
- **Brand palettes** are the commercetools brand colors.
- **System palettes** cover the full range of hues. Use them for decoration or
  to tell items apart, for example tags in different colors.

A semantic palette has no colors of its own. It points to a brand or a system
palette, so `primary.9` and `ctviolet.9` are the same color. Use the semantic
name: if Nimbus changes the palette it points to, your UI changes with it.

| **Semantic palette** | **Meaning**                                              | **Points to** |
| -------------------- | -------------------------------------------------------- | ------------- |
| `primary`            | The main color; the default of components such as Button | `ctviolet`    |
| `neutral`            | No status; the gray of text, borders and surfaces        | `gray`        |
| `info`               | Information                                              | `blue`        |
| `positive`           | Success or a positive state                              | `grass`       |
| `warning`            | A warning                                                | `amber`       |
| `critical`           | An error, a critical state or a destructive action       | `red`         |

### Light and dark mode

Every step has two values: one for light mode and one for dark mode. The token
name stays the same, so `primary.3` is a light violet in light mode and a dark
violet in dark mode. Components and your own styles follow the color mode, so
you do not need a separate design for dark mode.

Use the **Light** and **Dark** buttons in the palette browser to compare both
values. Only the [black and white palettes](#black-and-white-palettes) keep the
same value in both modes.

### Swap palettes

All palettes work the same way, the brand palettes included: each step has the
same job in every palette. So you can replace one palette with another, for
example `primary` with `critical`, and the design keeps its contrast levels and
its visual hierarchy. This is why a component can take any palette with the
`colorPalette` prop. The only exceptions are the
[black and white palettes](#black-and-white-palettes).

### Black and white palettes

`blackAlpha` and `whiteAlpha` work differently from all other palettes. Their
steps are black or white with more opacity at each step, from 5% at step 1 to
95% at step 12. These two palettes:

- do not change with the color mode: black is always black,
- have no `contrast` step,
- cannot be swapped with other palettes.

For a gray that follows the color mode, use `neutral`.

## Use colors in code

Refer to a color by its palette and step. Components take a palette with the
`colorPalette` prop and choose the steps themselves.

```tsx
// A palette and a step
<Box bg="primary.3" color="primary.11" borderColor="primary.7">
  content
</Box>

// A component with another palette
<Button colorPalette="critical" variant="solid">
  Delete
</Button>

// In a recipe, colorPalette stands for the palette the component gets
base: {
  bg: "colorPalette.9",
  color: "colorPalette.contrast",
}
```

## Accessibility and contrast

The palettes are built to be accessible. Their contrast levels are based on
[APCA (Accessible Perceptual Contrast Algorithm)](https://github.com/Myndex/APCA),
a method for calculating perceived contrast that accounts for human visual
perception more accurately than the traditional WCAG 2.x formula.

> [!NOTE]\
> Some automated accessibility tools still use the older WCAG 2.x synthetic
> contrast calculation (4.5:1 ratio), which can produce false positives for
> certain color combinations that APCA considers accessible. If your tooling
> flags contrast issues with these pairings, verify the results against an
> APCA-based checker before making changes.

## Where the colors come from

The system palettes and the use case of each step come from
[Radix Colors](https://www.radix-ui.com/colors). Nimbus adds:

- the brand palettes: commercetools colors in the same 12-step form,
- the semantic palettes, which point to a brand or a system palette,
- the `contrast` step, which Nimbus calculates for each palette.

To learn how Radix designs each step, see the
[Radix color scale documentation](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale).
