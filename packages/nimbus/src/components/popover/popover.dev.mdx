## Getting started

### Import

```tsx
import {
  Popover,
  type PopoverRootProps,
  type PopoverTriggerProps,
  type PopoverContentProps,
} from "@commercetools/nimbus";
```

### Basic usage

Popover is a compound component with three parts. `Root` owns the open state and
the styling context, `Trigger` opens it, and `Content` is the positioned surface.

```jsx live-dev
const App = () => (
  <Popover.Root>
    <Popover.Trigger>Open popover</Popover.Trigger>
    <Popover.Content aria-label="Example popover">
      <Text>Content goes here.</Text>
    </Popover.Content>
  </Popover.Root>
);
```

Three things about this structure are worth knowing up front:

- **`Root` renders no DOM element.** It wraps React Aria's `DialogTrigger`, which
  is a context provider, so it adds nothing to your layout. A trigger inside a
  flex row stays where you put it.
- **`Content` supplies its own dialog.** You do not add `<Dialog>` yourself.
  React Aria needs a dialog inside a popover for the role, name and Escape
  handling to work, so `Content` owns it.
- **`Trigger` renders a bare `button`.** Its slot adds a focus ring and nothing
  else, so the form above gives you browser default chrome. Reach for `asChild`
  with a `Button` or `IconButton` when you want Nimbus styling, as the later
  examples do.

## Usage examples

### Uncontrolled mode

`defaultOpen` sets the initial state and lets the component manage it from
there.

This one is shown as code rather than rendered live: a `defaultOpen` popover is
modal from the moment it mounts, so a live example would open over the page,
contain focus and hide the surrounding documentation from assistive technology
as soon as you scrolled to it.

```tsx
<Popover.Root defaultOpen>
  <Popover.Trigger>Open popover</Popover.Trigger>
  <Popover.Content aria-label="Initially open">
    <Text>Open on mount.</Text>
  </Popover.Content>
</Popover.Root>
```

### Controlled mode

Pass `isOpen` and `onOpenChange` to own the state. In controlled mode the popover
does not close itself — it reports the request and waits for `isOpen` to change.

```jsx live-dev
const App = () => {
  const [isOpen, setIsOpen] = useState(false);

  return (
    <Stack gap="200">
      <Popover.Root isOpen={isOpen} onOpenChange={setIsOpen}>
        <Popover.Trigger>Toggle popover</Popover.Trigger>
        <Popover.Content aria-label="Controlled popover">
          <Text>Controlled by the parent.</Text>
        </Popover.Content>
      </Popover.Root>
      <Text>State: {isOpen ? "open" : "closed"}</Text>
    </Stack>
  );
};
```

### Closing from inside the content

Because `Content` owns the dialog, buttons inside it can use `slot="close"`,
the same way they do in `Dialog` and `Drawer`:

```jsx live-dev
const App = () => (
  <Popover.Root>
    <Popover.Trigger>Discard changes</Popover.Trigger>
    <Popover.Content aria-label="Discard changes">
      <Stack gap="200">
        <Text>Discard your changes?</Text>
        <Button slot="close">Discard</Button>
      </Stack>
    </Popover.Content>
  </Popover.Root>
);
```

Reach for a function child instead when the action has to do something *before*
it dismisses — `Content` forwards React Aria's `close` render prop, so the
callback can run inside your own handler. Either way, prefer these over wiring
up controlled state just to close the popover.

```jsx live-dev
const App = () => (
  <Popover.Root>
    <Popover.Trigger>Discard changes</Popover.Trigger>
    <Popover.Content aria-label="Discard changes">
      {({ close }) => (
        <Stack gap="200">
          <Text>Discard your changes?</Text>
          <Stack direction="horizontal" gap="200">
            <Button variant="outline" onPress={close}>
              Cancel
            </Button>
            <Button onPress={close}>Discard</Button>
          </Stack>
        </Stack>
      )}
    </Popover.Content>
  </Popover.Root>
);
```

### Custom triggers

Without `asChild`, `Trigger` renders its own button. With `asChild`, it applies
trigger behavior to the element you supply, which avoids nesting one interactive
element inside another.

```jsx live-dev
const App = () => (
  <Popover.Root>
    <Popover.Trigger asChild>
      <IconButton aria-label="Options" size="xs" variant="ghost">
        <Icons.MoreVert />
      </IconButton>
    </Popover.Trigger>
    <Popover.Content aria-label="Options">
      <Text>Options list</Text>
    </Popover.Content>
  </Popover.Root>
);
```

The two modes accept different props. React Aria delivers the trigger contract —
press handling, `aria-expanded`, `aria-controls` and the trigger ref — to the
rendered element through context, so with `asChild` there is nothing for
`Trigger` to forward. Put the element's own props (`id`, `aria-label`,
`isDisabled`) on the element itself; `Trigger` accepts only style props in this
mode, and rejects the rest at compile time rather than accepting them and having
no effect.

### Positioning

`placement` accepts a side, optionally followed by an alignment. The alignment
values depend on the axis — this trips people up, so it is worth stating
explicitly:

| Side | Valid alignments |
| --- | --- |
| `top`, `bottom` | `left`, `right`, `start`, `end` |
| `left`, `right`, `start`, `end` | `top`, `bottom` |

So `bottom start` and `right top` are valid; `right start` is not, and will fail
to typecheck.

```jsx live-dev
const App = () => (
  <Popover.Root placement="right top" offset={12} crossOffset={4}>
    <Popover.Trigger>Positioned</Popover.Trigger>
    <Popover.Content aria-label="Positioned popover">
      <Text>placement="right top"</Text>
    </Popover.Content>
  </Popover.Root>
);
```

`offset` adjusts distance along the trigger's axis, `crossOffset` along the
perpendicular one, both in pixels. `shouldFlip` (default `true`) controls whether
the popover may flip to the opposite side to stay in the viewport.

### Where configuration goes

`Popover.Root` is the configuration surface for the whole compound — the only
one. It renders React Aria's `DialogTrigger`, but it also accepts the behavioral
props of the `Popover` and `Dialog` elements that `Popover.Content` renders on
its behalf, and passes them along internally.

`Popover.Content` accepts none of them. There is exactly one `Popover.Content`
per `Popover.Root`, so a second place to set the same option would only be a
second place to look for it:

```jsx live-dev
const App = () => (
  <Popover.Root placement="right top" offset={12} maxHeight={320}>
    <Popover.Trigger>Configured on Root</Popover.Trigger>
    {/* placement, offset and the height cap all belong on Root */}
    <Popover.Content aria-label="Configured popover">
      <Text>Content carries only its own styling and labelling.</Text>
    </Popover.Content>
  </Popover.Root>
);
```

What `Popover.Content` does own is how its own two elements look: style props for
the positioned surface, and `id` / `className` / `data-*` / the labelling `aria-*`
/ pointer and animation event handlers for the dialog inside it. React Aria
filters that second set, so keyboard and focus handlers (`onKeyDown`, `onFocus`,
`onBlur`), `title`, `tabIndex` and any non-labelling `aria-*` are accepted by the
type but never reach the DOM — put those on your own content element.

The full set of behavioral props, all on `Popover.Root`:

| Prop | Purpose |
| --- | --- |
| `placement`, `offset`, `crossOffset` | Side, alignment and distance from the trigger |
| `shouldFlip` | Allow flipping to the opposite side to stay visible |
| `containerPadding`, `boundaryElement` | Viewport-collision boundary and its padding |
| `isNonModal` | Leave outside content reachable |
| `isKeyboardDismissDisabled` | Disable Escape to close |
| `shouldCloseOnInteractOutside` | Filter which outside interactions dismiss |
| `triggerRef` | Anchor to an element other than the trigger |
| `maxHeight` | Numeric cap on the surface height, in pixels |
| `shouldUpdatePosition` | Set `false` to freeze position on scroll and resize |
| `scrollRef` | Nominates the scrollable region inside the overlay |
| `getTargetRect` | Anchors to an arbitrary rect — a cursor point or text selection |
| `trigger` | Sets `data-trigger` on the surface, for trigger-dependent styling |
| `isEntering`, `isExiting` | Drive the enter and exit animations externally |
| `shouldSkipAnimation` | Suppresses animation, e.g. when swapping along one axis |
| `UNSTABLE_portalContainer` | Renders the overlay into a container other than `document.body` |
| `onFocusWithin`, `onBlurWithin`, `onFocusWithinChange` | Focus tracking across the whole surface |
| `role` | `"dialog"` (default) or `"alertdialog"`, applied to the dialog element |
| `arrowRef`, `arrowBoundaryOffset` | Arrow positioning — inert, as Nimbus renders no arrow |

> [!NOTE]\
> Three of those names — `role`, `offset` and `maxHeight` — also exist in the DOM
> and Chakra prop surfaces that `Popover.Content` is derived from, so Content
> excludes them by name. `role` is the one that matters: it is not a style prop,
> so without the exclusion it would be accepted and then dropped — Content
> re-applies Root's `role` after spreading the rest — and its DOM type admits
> roles the dialog rejects. A CSS height cap would not work on Content either
> way — React Aria assigns `overlay.style.maxHeight` on every position pass, and
> that inline value always beats a Chakra class, which is why the still-accepted
> `maxH` alias cannot take effect on this element either. Root's `maxHeight` is
> also the semantically correct one: it feeds the placement calculation rather
> than clipping a box that has already been positioned.

The open-state props — `isOpen`, `defaultOpen` and `onOpenChange` — live on
`Popover.Root` and nowhere else, because the trigger and the surface have to
share one state.

### Dismissal behavior

By default the popover closes on Escape and on an outside press. Both can be
adjusted:

```jsx live-dev
const App = () => (
  <Popover.Root isKeyboardDismissDisabled>
    <Popover.Trigger>Keyboard dismiss disabled</Popover.Trigger>
    <Popover.Content aria-label="No Escape dismissal">
      <Text>Escape will not close this. Click outside instead.</Text>
    </Popover.Content>
  </Popover.Root>
);
```

`shouldCloseOnInteractOutside` takes a predicate receiving the interacted
element, so you can exempt specific regions from dismissing the popover.

> [!CAUTION]\
> If you set `isKeyboardDismissDisabled`, provide another keyboard route to close
> the popover. Otherwise keyboard users can open something they cannot dismiss.

### Styling

Style props on `Trigger` and `Content` apply to that part's slot. `Root` renders
no element, so it takes none. Padding lives on the content surface, so a single
prop removes it:

```jsx live-dev
const App = () => (
  <Popover.Root>
    <Popover.Trigger>Flush content</Popover.Trigger>
    <Popover.Content padding="0" maxWidth="4800" aria-label="Flush popover">
      <Box padding="300" backgroundColor="primary.2">
        <Text>Zero padding on the surface.</Text>
      </Box>
    </Popover.Content>
  </Popover.Root>
);
```

## Component requirements

### Accessibility

The Popover component handles most accessibility requirements internally via
React Aria.

- **Labeling**: `Popover.Content` renders a dialog, so it needs an accessible
  name. Pass `aria-label`, or `aria-labelledby` pointing at a heading inside the
  content. This is the one accessibility requirement the component cannot satisfy
  for you.
- **Role**: `Content` renders an element with `role="dialog"`.
- **Focus management**: focus moves into the dialog on open and returns to the
  trigger on close. The exception is a dismissing press on another focusable
  element, which leaves focus on that element.
- **ARIA state**: the trigger carries `aria-expanded`, plus `aria-controls` while
  open. It deliberately does not carry `aria-haspopup` — React Aria sets that only
  for `menu` and `listbox` overlays, since screen readers often announce other
  values as "menu".

By default focus is contained within the popover and outside interaction
dismisses it. `isNonModal` changes neither: it stops React Aria marking the rest
of the page `inert` and locking page scroll, so assistive technologies can reach
the surrounding page, while focus stays inside the dialog. React Aria's guidance
is that most popovers should not use it.

If your use case requires tracking and analytics for this component, it is good
practice to add a **persistent**, **unique** id:

```tsx
const PERSISTENT_ID = "filters-popover-trigger";

export const Example = () => (
  <Popover.Root>
    <Popover.Trigger id={PERSISTENT_ID}>Filters</Popover.Trigger>
    <Popover.Content aria-label="Filters">…</Popover.Content>
  </Popover.Root>
);
```

`Popover.Content` takes an `id` too. It lands on the dialog element, and React
Aria re-points the trigger's `aria-controls` at it, so the trigger-to-overlay
link is kept. `data-*` attributes and click handlers on `Popover.Content` reach
the same element. `Popover.Root` takes neither — it renders nothing.

#### Keyboard navigation

The component supports full keyboard interaction:

- `Tab`: moves focus between focusable elements inside the popover
- `Enter` or `Space`: toggles the popover when the trigger is focused
- `Escape`: closes the popover and returns focus to the trigger

### Composition constraints

- `Popover.Trigger` and `Popover.Content` must be inside a `Popover.Root`.
- Do not add your own `Dialog` inside `Popover.Content` — it already renders one,
  and nesting a second breaks the naming and focus contract.
- Do not nest a Popover inside another Popover.

## Common patterns

### Filter panel

```jsx live-dev
const App = () => {
  const [onlyActive, setOnlyActive] = useState(false);

  return (
    <Popover.Root>
      <Popover.Trigger>Filters</Popover.Trigger>
      <Popover.Content aria-labelledby="filters-title" maxWidth="4800">
        {({ close }) => (
          <Stack gap="300">
            <Heading id="filters-title" size="sm">
              Filters
            </Heading>
            <Checkbox isSelected={onlyActive} onChange={setOnlyActive}>
              Only active
            </Checkbox>
            <Button onPress={close}>Apply filters</Button>
          </Stack>
        )}
      </Popover.Content>
    </Popover.Root>
  );
};
```

### Inline edit

```jsx live-dev
const App = () => {
  const [name, setName] = useState("Ada Lovelace");
  const [draft, setDraft] = useState(name);

  return (
    <Stack direction="horizontal" gap="200" alignItems="center">
      <Text>{name}</Text>
      <Popover.Root onOpenChange={(open) => open && setDraft(name)}>
        <Popover.Trigger asChild>
          <IconButton aria-label="Edit name" size="2xs" variant="ghost">
            <Icons.Edit />
          </IconButton>
        </Popover.Trigger>
        <Popover.Content aria-label="Edit name">
          {({ close }) => (
            <Stack gap="200">
              <TextInput
                aria-label="Name"
                value={draft}
                onChange={setDraft}
              />
              <Button
                onPress={() => {
                  setName(draft);
                  close();
                }}
              >
                Save
              </Button>
            </Stack>
          )}
        </Popover.Content>
      </Popover.Root>
    </Stack>
  );
};
```
